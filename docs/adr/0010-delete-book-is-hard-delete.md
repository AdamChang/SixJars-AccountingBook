# 刪除整本帳本採硬刪除，只留一筆摘要稽核記錄

擁有者可以從 Web 刪除整本帳本（issue #6）。帳本、帳戶、分類、財務規劃帳戶、交易（含已軟刪除的）、預定支出、週期預定支出、預算、帳本成員，以及這本帳本**所有既有的稽核記錄**，都會從資料庫實際移除，最後只寫一筆 `Delete`／`Book` 的稽核記錄。這筆記錄的 `Before` 是刪除當下的摘要（名稱、開帳日、鎖帳日、各類筆數），不含任何交易內容。這是 ADR 0006「刪除一律採軟刪除」的例外：0006 處理的是**單筆**資料的誤刪；整本帳本的刪除則經過確認（使用者必須輸入帳本名稱），是明確表示要清掉這本帳本。典型情境是匯入錯誤後，以同一個名稱重新匯入。

## Considered Options

- **軟刪除帳本（`Book.DeletedAt`）**：資料雖然還在，名稱卻一直被佔用，同名重新匯入會被擋下；Web 也沒有救回資料的入口，結果只剩成本。
- **保留舊的稽核記錄**：舊快照包含完整的交易內容，留著就等於沒有刪除。
- **補上 FK `ON DELETE CASCADE`，只刪 `Book`**：之後任何誤刪 `Book` 的程式碼都會清空整本帳本，而且這是 DB 的隱性行為，測試難以表達。因此改在 handler 裡逐表明確刪除，再由 convention test 確保新增帶 `BookId` 的資料表時不會漏刪。
- **伺服器端自動備份**：部署環境沒有 object storage，保留期限與清理也是額外負擔。改為在刪除前提示使用者下載既有的 JSON 備份。

## Consequences

- 刪除後無法救回，除非使用者事先下載了備份，再用 CLI `restore-backup` 還原。
- 刪除期間不鎖定帳本。若同時有其他寫入，可能留下 `BookId` 指向不存在帳本的孤兒資料；這些資料不會出現在任何查詢中（非成員一律 404）。家庭帳本幾乎沒有這種並行情境，因此接受這個風險。
- 新增帶 `BookId` 的資料表時，必須同時更新 `DeleteBookHandler`；`DeleteBookEndpointsTests` 的 convention test 會擋下遺漏。
- 刪除摘要的稽核記錄目前沒有 UI 可以查看，因為帳本已不存在，稽核 API 會回 404。之後的稽核查詢介面需要另外處理這類記錄。
