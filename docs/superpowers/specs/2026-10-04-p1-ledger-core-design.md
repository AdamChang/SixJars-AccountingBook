## 2. 架構決策

### D1. 分兩段：先純 Domain，末段再加持久層

P1 的主要風險是「規則正確性」，與資料怎麼存無關，所以分成兩段做：

- **段 A（純 Domain）**：Domain、匯入與逐月驗收全部在記憶體中運作。段 A 結束時是第一個 checkpoint，到這裡就可以收工。
- **段 B（持久層）**：EF Core + PostgreSQL mapping 與 migration。驗收重跑一次「匯入 → 存檔 → 用新的 DbContext 載入 → 數字仍與 Excel 一致」，讓持久層的形狀直接用真實資料驗證。

否決的方案：

- **否決：持久層從第一個 Task 就一起做。** 規則錯誤和 mapping 錯誤會混在一起除錯。
- **否決：持久層全部延到 P2。** Docker 已經可用，在有真實資料可以驗證的時候順便驗證持久層，成本最低。

### D1-b. 持久層設計（段 B）

- **分錄實體化存檔**：存成 `postings` 表，作為 Transaction 的 owned collection，讓 P2 的餘額查詢可以直接在 SQL 中 `SUM`（ADR 0001）。P1 段 B 只驗證「存得進去、載得回來」，計算仍然由 Domain 的計算器負責；SQL 端的彙總查詢等 P2 有 API 時再做。
  - **否決：讀取時才展開分錄。** 這樣展開規則會滲進查詢路徑，P2 的餘額查詢也無法下推到資料庫。
- **歸屬月份**存成 `int`（yyyymm），可以直接排序與比較；`DateOnly` 由 Npgsql 原生對應到 `date`。
- Transaction 和 PlannedExpense 從一開始就帶 `BookId`，為日後的多帳本或家人共用（Q6）保留邊界。
- 套件與測試：Npgsql EF Core provider；整合測試用 Testcontainers 的 PostgreSQL 17 映像（Supabase 支援的主要版本）。
- P1 不需要任何連線字串設定檔。測試的連線來自容器，Supabase 的連線設定留到 P2，並且透過環境變數提供。

### D2. 專案切分（Clean Architecture 的 P1 子集）

```
src/SixJars.Domain          實體、值物件、分錄展開、計算器（純函式，無相依）
src/SixJars.Application     LegacyImport：Excel 列 → Domain 的轉換規則（純，無 I/O）
src/SixJars.Infrastructure  LegacyExcel：讀 xlsm → 原始列 DTO（唯一碰檔案的地方）
                            Persistence：EF Core DbContext、mapping、migration（段 B）
tests/SixJars.Domain.Tests
tests/SixJars.Application.Tests
tests/SixJars.Infrastructure.Tests   持久層往返測試（Testcontainers，段 B）
tests/SixJars.AcceptanceTests        讀真實 xlsm → 轉換 →（段 B：存檔再載入）→ 逐月比對
```

匯入拆成「讀取」與「轉換」兩段，讓 Excel 語意的轉換規則（本專案最容易錯的地方）能用合成資料做單元測試，不必依賴那份個資檔案。MediatR 與 FluentValidation 等 P2 有 API 時才引入，P1 沒有 request 可以處理。

### D3. 聚合邊界

- **Book**（聚合根）：帳戶、財務規劃帳戶、分類、期初日。這些是設定類資料，數量少、彼此參照。
- **Transaction**（獨立聚合）：以 Id 參照帳戶、分類、財務規劃帳戶。建立時由 `TransactionFactory` 依 Book 驗證規則（例如繳卡費只能由現金或銀行支付）並展開分錄。分錄是 Transaction 內部的值物件，編輯交易時整組重新產生。
- **PlannedExpense**（獨立聚合）：以 Id 參照分類、帳戶，以及付款後連結的交易。
- 計算器吃一個唯讀的 `LedgerSnapshot`（Book + 交易 + 預定支出），P1 由記憶體集合提供，P2 改由查詢提供。

- **否決：所有交易放在 Book 聚合裡。** P2 接上 EF 之後，每次寫入都得載入整本帳。

### D4. 金額與符號

- 金額型別用 `decimal`。Excel 中有 `9874.3`、`4580.6` 這類小數（交易所的台幣價值）。
- **分錄符號採資產觀點**：資產帳戶的正數代表餘額增加；負債帳戶（信用卡、貸款）的餘額為負數。
  - 信用卡**尚待繳清**＝−餘額；貸款**剩餘本金**＝−餘額。
- 收入和支出的輸入金額沿用 Excel 慣例：支出輸入負數，退款或折抵輸入正數。轉帳類交易的金額恆為正，方向由「從 → 到」決定。

### D5. 期初

`Book.OpeningDate`，加上每個帳戶、財務規劃帳戶各自的 `OpeningBalance`。期初**不是**一筆交易。帳戶餘額(asOf) = 期初 + Σ 該帳戶在 asOf 之前（含）的分錄。
匯入時，`OpeningDate` 設為最早一筆交易日期的前一天（Q22）。

## 3. 分錄展開規則

`A` 是主帳戶，`C` 是對方帳戶，`x` 是金額。

| 交易類型 | 分錄 | 財務規劃帳戶 | 帳戶限制 |
|---|---|---|---|
| Income 收入 | A += x | — | A：現金、銀行、電子錢包 |
| Expense 支出 | A += x（x 通常為負） | — | A：任何非貸款帳戶 |
| Transfer 轉帳 | from −x, to +x | — | 兩端皆為現金或銀行 |
| Withdrawal 提款 | bank −x, cash +x | — | |
| CashDeposit 現金存入 | cash −x, bank +x | — | |
| TopUp 加值 | source −x, wallet +x | — | source：現金、銀行、信用卡 |
| CardPayment 繳卡費 | payer −x, card +x | — | payer：現金、銀行 |
| LoanDisbursement 新增貸款 | loan −x, receiver +x | — | receiver：現金、銀行 |
| LoanPayment 貸款繳款 | payer −x, loan +principal | — | 利息 = x − principal，記為支出（不入任何帳戶） |
| FundAllocation 入新資金 | 若 from≠to：from −x, to +x | fund +x | from 可為空（同帳戶內圈存） |
| FundWithdrawal 出資金 | A −x | fund −x | 分類可選填 |
| FundReturn 資金回流 | A +x | fund +x | |

## 4. 計算

### 4.1 月可用餘額（依歸屬月份 M）

```
  Σ Income.x
+ Σ Expense.x            where A.Type ≠ EWallet   （電子錢包消費不計）
− Σ TopUp.x
− Σ FundAllocation.x
− Σ LoanPayment.x        （本金＋利息全額）
+ Σ 未付 PlannedExpense.Estimated   （負數）
```

轉帳、提款、現金存入、繳卡費、新增貸款、出資金、資金回流都**不影響**月可用餘額。

### 4.2 年累計餘額 ＝ 當年 1..M 月的月可用餘額加總。

### 4.3 為什麼驗收比對 `J6 − N5`

勾選「含電子錢包」時，Excel 的 `J6` 會加上所有電子錢包的**目前餘額**（`N5 = M30`），這是存量混進流量（Q25）。本系統的月可用餘額是純流量，所以比對時要把 `N5` 扣掉。

### 4.4 驗收用的「依歸屬月份截止」餘額

Excel 的各月帳戶餘額是「累計到該工作表為止」，也就是依**歸屬月份**截止，而不是依日期。例如 1/30 的薪資在 2 月工作表，Excel 的 1 月底餘額不含這筆。所以：

- 產品功能（資產負債表）用 `BalanceAsOf(date)`（Q37）。
- 驗收比對另外提供 `BalanceThroughBudgetMonth(M)`：期初 + Σ 歸屬月份 ≤ M 的分錄。

兩種截止方式都是 Domain 正式提供的查詢，不是只寫在測試裡的 hack，因為 P3 的月報表也需要後者。

### 4.5 可用現金 ＝ Σ 計入可用現金的現金帳戶餘額（＋可選的電子錢包餘額）。

### 5.2 流水帳列（各月 `AH:AM`）→ 交易

判斷順序如下，第一個符合的規則生效：

| 主選單 | 副選單 | → 交易類型 |
|---|---|---|
| 轉帳 | 帳戶 | Transfer；x>0：from=副、to=方式；x<0：from=方式、to=副；金額取絕對值 |
| 提款 | — | Withdrawal（bank=方式、cash=現金） |
| 現金存入 | — | CashDeposit |
| 加值 | 來源帳戶 | TopUp（wallet=方式） |
| 繳信用卡款 | 卡 | CardPayment |
| 新增貸款 | 貸款 | LoanDisbursement |
| 貸款支出 | 貸款 | LoanPayment（本金見 5.4） |
| 財務規劃帳戶名稱 | 帳戶 | FundAllocation（to=方式、from=副） |
| 財務規劃帳戶名稱 | 出資金 | FundWithdrawal |
| 財務規劃帳戶名稱 | 資金回流 | FundReturn |
| 收入項目 | 任意 | Income |
| 固定支出 | 項目 | Expense，分類 = 固定支出項目 |
| 其他 | 任意 | Expense，分類 = 主／副選單 |

- 方式「非手上現金」→ 外幣現鈔帳戶。
- 主選單「手續費」（銀行的方式選單）→ 支出，分類為「金融交易／手續費」（3 月第 20 列有一筆）。
- 「方式＝現金」並且搭配財務規劃帳戶，副選單是「入新資金」或銀行（現金放進實體信封，Q26）→ 不支援，列入錯誤清單（1–3 月沒有這種資料）。
- 歸屬月份 = 工作表月份。
- **日期異常**：日期與工作表月份相差超過 6 個月時（例如 1 月表中的 2026-12-31），把年份修正到最接近工作表月份的那一年，並列入匯入報告。
- 無法分類的列（未知帳戶、未支援的組合，例如「方式＝現金、副選單＝入新資金」）→ 列入匯入報告的錯誤清單，**不匯入**。驗收測試要求錯誤清單為空。

### 5.3 制式表格（固定、貸款、特別支出）→ 預定支出

| 狀況 | 轉成 |
|---|---|
| 有支出日、有方式 | 已付的預定支出＋一筆交易（固定或特別支出 → Expense；貸款 → LoanPayment），交易日期 = 支出日 |
| 沒有支出日 | 未付的預定支出 |
| 有支出日但沒有方式（例如 2 月 Youtube/Google −130） | 未付的預定支出，並列入匯入報告的警告清單（和 Excel 一樣：扣月可用餘額，但不扣任何帳戶） |

### 5.4 貸款本金分攤

每月的「本月還本金」（貸款區 `N` 欄）是該貸款當月的本金**總額**。分攤規則：

1. 流水帳中的「貸款支出」視為提前還本：本金 = 繳款全額。
2. 剩下的本金全部分給制式表格的貸款繳款。
3. 若分攤後的本金 < 0，或大於繳款金額 → 列入匯入錯誤。

查證：2 月本金 88,131 = 60,000（流水帳提前還本）+ 28,131（制式表格）。

### 5.5 分類

`清單` 工作表的浮動支出主選單（`AV2:BT2`）和其下的副選單 → 支出性質為「浮動」的主分類＋子分類。
`設定` 的固定支出項目 → 「固定」主分類下的子分類；貸款項目 → 「貸款」性質；收入項目 → 收入分類。
空白和「自定浮支NN」這類佔位名稱不匯入。
